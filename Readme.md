# How the Monorepo was Set Up

This guide walks through, step by step, how the `equipment-maintenance-hub` npm-workspaces monorepo was built, in the order it was done.

## Prompt for Claude Code in VSCode

```
Create an npm-workspaces monorepo named "equipment-maintenance-hub".

Requirements:
- Root package.json with "private": true and workspaces ["apps/*", "packages/*"].
- Empty packages: apps/backend, apps/frontend, packages/contract.
- Each package uses pure ESM with "type": "module".
- Backend and frontend depend on "@equipment-hub/contract": "*".
- Add a Node-oriented .gitignore for node_modules, dist, coverage, .turbo, and local env files.
- Do not add application dependencies yet.

Show the resulting folder tree and explain how npm install creates the local workspace link for @equipment-hub/contract
```

## 1. Create the workspace folders

```bash
mkdir -p apps/backend apps/frontend packages/contract
```

npm workspaces don't need any special "init" command — a workspace is just any folder matched by the `workspaces` glob in the root `package.json` that contains its own `package.json`. So the first step is simply creating the folders that will become workspaces.

## 2. Write the root `package.json`

```json
{
  "name": "equipment-maintenance-hub",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "workspaces": [
    "apps/*",
    "packages/*"
  ]
}
```

Key points:
- `"private": true` — required by npm whenever `workspaces` is used, and it also stops the root package from ever being accidentally published.
- `"workspaces"` uses glob patterns (`apps/*`, `packages/*`) rather than listing each package by name, so new packages just need a folder — no root config change.
- `"type": "module"` makes the root itself ESM too, for consistency (not strictly required, since the root has no source files).

## 3. Write each package's `package.json`

**`packages/contract/package.json`** — the shared package, no dependencies yet:
```json
{
  "name": "@equipment-hub/contract",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "main": "index.js"
}
```

**`apps/backend/package.json`** and **`apps/frontend/package.json`** — both depend on the contract package using npm's workspace wildcard:
```json
{
  "name": "@equipment-hub/backend",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "main": "index.js",
  "dependencies": {
    "@equipment-hub/contract": "*"
  }
}
```

Notes:
- All packages are scoped under `@equipment-hub/` so their names don't collide with anything on the public npm registry.
- `"type": "module"` is set on every package individually — Node.js checks the *nearest* `package.json` to a file, not just the root, so each workspace needs its own.
- The dependency version `"*"` tells npm "use whatever version of this package lives in the workspace," which is the idiomatic way to reference a sibling workspace package.
- No application dependencies (Fastify, React, Vite, etc.) were added — that's deliberately left for a later step.

## 4. Add a `.gitignore`

A standard Node-oriented ignore file was added covering:
- `node_modules/` — reinstalled from `package-lock.json`, never committed
- `dist/`, `build/` — compiled output
- `coverage/` — test coverage reports
- `.turbo/` — Turborepo's local cache, in case a task runner is added later
- `.env`, `.env.local`, `.env.*.local` — local secrets/config that shouldn't be committed
- plus a few standard extras (log files, `.DS_Store`)

## 5. Run `npm install` and verify the link

```bash
npm install
```

This does two things at once:
1. Installs any *external* dependencies (there are none yet).
2. Wires up the *internal* workspace dependencies — since `apps/backend` and `apps/frontend` both ask for `@equipment-hub/contract`, and npm finds a package with that exact name already inside the workspace, it does **not** hit the registry for it. Instead it creates a symlink:

   ```
   node_modules/@equipment-hub/contract -> packages/contract
   ```

   (verified after running install — `backend` and `frontend` get similar self-referential symlinks too, since every workspace member is also linked into the shared root `node_modules`).

Because it's a symlink rather than a copied file, any `import` from `@equipment-hub/contract` in the backend or frontend resolves live to the source files in `packages/contract` — no rebuild or republish step is needed to see changes.

## Result

```
equipment-maintenance-hub/
├── .gitignore
├── package.json                # root, workspaces: ["apps/*", "packages/*"]
├── package-lock.json           # generated by npm install
├── apps/
│   ├── backend/package.json    # @equipment-hub/backend
│   └── frontend/package.json   # @equipment-hub/frontend
└── packages/
    └── contract/package.json   # @equipment-hub/contract
```

## Commands to Run and Verify (Windows Terminal / PowerShell)

At this stage there's no application code or dependencies yet (no Fastify, React, or Vite), so there's nothing to "run" as an app. What you *can* do is verify the workspace wiring is correct.

**1. Navigate to the project**
```powershell
Set-Location "c:\0. IMPORTANTE - atmira---Curso-AI-SDD-main\Curso Udemy 1 AI Para programadores\Project equipment_maintenance_hub_React_Vite_Fastify_TypeScrip\Prompt1 Monorepo Foundation"
```

**2. Install dependencies and create the workspace links**
```powershell
npm install
```

**3. Verify all workspaces are recognized and linked correctly**
```powershell
npm ls --workspaces
```
Expected output: `backend` and `frontend` both show `@equipment-hub/contract` as a dependency, `deduped`, pointing at `.\packages\contract`.

**4. List just the workspace names npm sees**
```powershell
npm query .workspace
```

**5. Confirm the physical symlinks on disk**
```powershell
Get-Item "node_modules\@equipment-hub\*" | Select-Object Name, LinkType, Target
```

**6. Run a command inside one specific workspace** (useful once there's actual code/scripts)
```powershell
npm run <script-name> --workspace=@equipment-hub/backend
```

Once application code and dev scripts (e.g. `dev` for Fastify/Vite) are added in a later step, this section will be updated with the real `npm run dev` commands to launch the backend and frontend.
